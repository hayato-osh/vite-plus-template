# スキルの書き方

出典: https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices

## 置き場所

- `.agents/skills/<name>/SKILL.md` に置く (`.claude/skills` はシンボリックリンク)。
- 追加したら `AGENTS.md` の「スキル」節に 1 行足す。
- 既存スキル (`pr`, `testing`) と同じく日本語、常体で書く。

## 手順

```
- [ ] 1. スキル無しでタスクをやらせ、失敗・毎回補足した情報を書き出す
- [ ] 2. それを突く評価シナリオを 3 つ作る (下記)
- [ ] 3. 失敗を埋める最小限の SKILL.md を書く
- [ ] 4. 新しいセッション (スキルを読み込んだ別インスタンス) で実タスクを流し、挙動を観察する
- [ ] 5. 読まれなかった箇所・誤読された箇所を直して 4 に戻る
- [ ] 6. 末尾のチェックリストを通す
```

想像上の要件は書かない。観察した失敗だけを埋める。

評価シナリオの形式:

```json
{
  "skills": ["testing"],
  "query": "parseDate にテストを追加して",
  "expected_behavior": [
    "テストファイルを対象の隣に置く",
    "test.each を使い、ラベルに入力と期待結果を書く",
    "期待値を手計算したリテラルで書く"
  ]
}
```

## frontmatter

- `name`: 小文字・数字・ハイフンのみ、64 文字以内。`anthropic` / `claude` を含めない。動名詞形 (`processing-pdfs`) か名詞句 (`pdf-processing`) で統一。`helper` `utils` のような曖昧な名前は避ける。
- `description`: 1024 文字以内。**何をするか** と **いつ読むか** (ユーザーの言い回し、ファイル種別などのトリガー) を両方書く。起動判定に使われる唯一の情報なので最重要。
- description は三人称で書く (「〜を手伝えます」「あなたは〜に使える」は不可)。

```yaml
# 良い
description: git diff を解析してコミットメッセージを生成する。コミットメッセージを書くとき、ステージ済みの変更をレビューするときに使う。
# 悪い
description: ドキュメントを手伝う
```

## 本文

- **Claude が既に知っていることは書かない。** 各段落に「これはトークンに見合うか」と問う。ライブラリや形式の一般的説明は削る。
- 自由度を作業の壊れやすさに合わせる。
  - 高 (箇条書きの方針): やり方が複数あり文脈次第のとき。例: コードレビュー。
  - 中 (テンプレート・擬似コード): 推奨パターンがあるが多少の変化は許すとき。
  - 低 (実行するコマンドをそのまま): 手順を外すと壊れるとき。例: マイグレーション。「このコマンドを変更・追加フラグなしで実行する」と明記。
- 選択肢を並べない。デフォルトを 1 つ示し、例外時の代替だけ添える。
- 用語は 1 つに固定する (「フィールド」と「項目」を混ぜない)。
- 日付で分岐する記述 (「◯月以降は新 API」) を書かない。旧方式は `<details>` の「旧パターン」節に隔離する。
- 出力形式が重要なら、テンプレートか入出力の例を 2〜3 個示す。説明より例のほうが伝わる。
- 多段の作業はチェックリスト付きの手順にし、検証 → 修正 → 再検証のループを入れる。
- MCP ツールは完全修飾名 (`mcp__<server>__<tool>`) で書く。
- 依存に無いツールを使わせるなら、実行コマンドまで書く (`vp dlx -- <pkg> ...`)。インストール済みと仮定しない。

## ファイル分割 (段階的開示)

- SKILL.md 本文は 500 行未満。超えそうなら詳細を別ファイルへ出す。SKILL.md は目次として働かせる。
- 参照は SKILL.md から 1 段のみ。参照先からさらに参照させると部分読みで終わる。
- 100 行を超える参照ファイルは先頭に目次を置く。
- ファイル名は中身が分かるように (`reference/finance.md`。`doc2.md` は不可)。領域ごとに分けると無関係な部分を読まずに済む。

```markdown
**フォーム入力**: [FORMS.md](FORMS.md) を参照
**API リファレンス**: [reference.md](reference.md) を参照
```

## スクリプトを同梱する場合

- 決定的な処理 (検証・変換) は Claude に生成させずスクリプトにする。スクリプト本体はコンテキストを消費せず、出力だけが載る。
- 「実行する」のか「アルゴリズムの参考に読む」のかを明記する。
- エラーは Claude に丸投げせずスクリプト内で処理する。エラーメッセージは具体的に (「`signature_date` が無い。存在するのは: ...」)。
- 定数には根拠をコメントで残す (`TIMEOUT = 47` だけは不可)。
- 一括・破壊的な変更は「計画ファイルを作る → スクリプトで検証 → 実行」の順にする。

## チェックリスト

```
- [ ] description に「何をするか」と「いつ読むか」の具体的なキーワードがある
- [ ] Claude が既に知っている説明を含んでいない
- [ ] 本文 500 行未満、参照は 1 段
- [ ] 用語が一貫している、時期依存の記述が無い
- [ ] 例が具体的
- [ ] 手順に検証ステップがある (必要な場合)
- [ ] 使うツールの実行方法が書いてある (インストール済みと仮定していない)
- [ ] スクリプトのエラー処理・定数の根拠が明記されている (同梱する場合)
- [ ] 評価シナリオ 3 つを新しいセッションで通した
- [ ] 使うモデルすべて (Haiku は説明不足、Opus は説明過多になりやすい) で試した
- [ ] AGENTS.md のスキル一覧に追記した
```

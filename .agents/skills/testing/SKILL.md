# テストの書き方

テストの目的は「壊したら困る経路」を CI で塞ぐこと。カバレッジ率は追わない。壊れたら困る順に、安い層ほど厚く書く。
ロジックはコンポーネントから純粋関数に切り出し、純粋関数を Vitest の単体テストで守るのを基本にする。

## 規約

- テストファイルは対象の隣に `<name>.test.ts(x)`。実行は `vp test`。
- import は `vite-plus/test` から (`vitest` から直接 import しない。lint ルール `vite-plus/prefer-vite-plus-imports`)。
- `test` / `test.each` を使う (`it` は使わない)。
- 期待値は **仕様から手計算したリテラル** で書き、計算根拠を行末コメントに残す。実装の関数で期待値を作らない。
- テストファイルも `vp check` (lint・型チェック) の対象。

## ラベルには入力と期待結果を書く

- 「正常系」「異常系」のような意味の不明瞭な語を使わない。入力と期待される結果を平叙文で書く。
- 数式のような表現も使う。「以上、以下」より `>=`、「〇〇の場合は▲▲を返す」より `(〇〇) -> ▲▲`。
- 語彙はプロダクトの仕様書のものを使う。
- `%s` / `%j` は引数の順に消費されるので、ラベルに出したい値をタプルの先頭に置き、長い入力は後ろに置く。

```ts
// 悪い例
test.each([...])("正常系: %s", ...);

// 良い例
test.each([...])("%s は valid として判定される", ...);
test.each([...])("(入力 %j) -> %j", ...);
```

## `describe` は意味のある単位でのみ使う

- ファイル名を繰り返すだけの `describe` や「正常系 / 異常系」のグルーピングは不要。テスト対象が 1 つならフラットに書く。
- 使うのは、1 ファイルに複数のテスト対象があるときと、前提条件やセットアップが異なるテスト群を分けるとき。

## `test.each` で共通化する

- 同じパターンは `test.each` にまとめる。全ケースに同じアサーションがかかり、ケース追加が 1 行で済む。
- コーナーケース的な関心事 (同点、境界値など) は独立した `test.each` グループに分ける。
- 1 行 1 ケースが理想。フォーマッタに行をまとめられないよう、1 つめのケースの行末に空の行コメント `//` を入れる。
- 型引数でタプルを指定する。1 要素タプル `[string]` でも `(input)` で受ける (`([input])` と書くと文字列が分割代入されて先頭 1 文字になる)。

```ts
test.each<[number, number, number]>([
  [1, 2, 3], //
  [-1, 1, 0], // 負数を含む
])("%s + %s = %s", (a, b, expected) => {
  expect(add(a, b)).toBe(expected);
});
```

## 型とアサーション

- `{ ok: true, ... } | { ok: false, error }` のような判別可能ユニオンは、`if (!result.ok) expect.unreachable("...")` で型を絞り込んでから中身を見る。`expect(result.ok).toBe(true)` だけでは型が絞られない。
- 例外はメッセージで判定する: `toThrow(new FooError(message))`。これはクラス (prototype) を見ず、`name`・`message`・列挙可能な独自プロパティで比べるので、**エラークラス側で `name` を明示する** (`class FooError extends Error {}` のままだと素の `Error` でも通る)。
- UI にそのまま出すエラー文は完全一致で検証する。文言を変えたらテストも変える。

## 網羅性

批判的な目で次を確認する。

- 境界値 (0、負数、上限ちょうど、上限を 1 超えた値)
- 同値・同点
- 入力順の入れ替え
- 空入力
- 形式の揺れ (空白、区切り文字、全角半角)
